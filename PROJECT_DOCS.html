1What is CommunityOS

CommunityOS is an AI-first platform for housing society management. Residents type or speak to ARIA — their AI assistant — in plain language. ARIA understands intent, calls the right tools, enforces policy, and either replies directly or hands off to ops.

Behind ARIA sits T2T (Twin-to-Twin), a domain-agnostic protocol layer. T2T handles the parts every product needs: who is asking, are they allowed, what did they do, did anyone need to be notified. Pulling those concerns out of ARIA means we can add new products on the same trunk later without re-implementing trust.

2The Twin Model

What is a "twin"?

A twin is an AI representative bound to a real-world entity: a resident, a society's ops desk, ARIA itself. Each twin has a stable ID and a long-lived credential. Twins don't share inboxes — when something needs to happen between two parties, their twins exchange a T2T message.

TwinRepresentsTypical actions
tanmay_residentA resident's intentAsks ARIA to book, to raise tickets, to check dues
aria_assistantThe AI conciergeUnderstands intent, runs tools, drafts replies, escalates
communityos_opsSociety managementApproves bookings/escalations, broadcasts notices
Why model it this way? Treating every entity as a first-class twin gives us one auth model, one audit trail, and one policy surface for the whole platform. Adding a new role (say, a maintenance vendor) means registering a new twin — not refactoring the protocol.

3System Architecture

Why this layout matters

  • Single audit trail. Every state-changing action passes through T2T's audit log — compliance becomes a query, not a forensic hunt.
  • Independent failure surfaces. If T2T is briefly degraded, ARIA's read paths (list amenities, view notices) still serve. If ARIA is being deployed, T2T continues to track twins.
  • Scale where the load is. ARIA scales to chat traffic; T2T scales to authorization throughput. They don't have to scale together.
  • Predictable change. A society feature ships in ARIA without touching T2T. A policy change ships in T2T without re-deploying ARIA.

4T2T's Role

What flows through T2T (and what doesn't)

Not every byte goes through the protocol. Read-only operations are answered directly by ARIA in-process — no T2T hop. State changes always go through T2T.

OperationPathWhy
List amenitiesIn-processRead-only, no policy needed
Show available slotsIn-processRead-only
List events / dues / noticesIn-processRead-only
Book an amenityThrough T2TCapacity check, policy, audit

6Amenity Discovery

The discovery flow turns plain language ("show me all the gyms") into rich, browsable cards. The schema, intent classifier, tool layer, and frontend card protocol all line up so a single user query reliably produces a useful UI.

The amenity record

Every amenity is a row in the amenities table with these fields:

FieldPurpose
amenity_idUUID — preferred selector when names are ambiguous
name / display_nameShort name (gym) and human label (Greenfield Gym - Block A)
typeCanonical category (gym, pool, court_badminton, …) — drives filtering
descriptionOne-line description for the rich card
featuresJSON array — rendered as chips on the card
block · floor · locationWhere it lives — surfaces on the card and in ARIA's replies
capacity_per_slotHow many bookings per slot (enforced server-side)
open_time · close_timeGenerates the slot grid for the picker

7Booking with Disambiguation

The killer feature: when a user says "book gym at 7" and there are three gyms, ARIA refuses to silently pick. It returns a disambiguation list and asks the user to choose. This is the production property a naive bot can't fake.

Why this is production-grade: A naive booking bot picks one of the gyms by lexical match and the resident shows up at the wrong block. ARIA's disambiguation contract returns options instead, and the LLM is instructed to ask the user to pick. This pattern is reusable for any multi-instance booking — it's not gym-specific.

8Bylaw Lookup with Citations

Canadian condo boards spend hours every week answering the same questions: "Can I install hardwood floors?", "Are pets allowed?", "What's the rule on Airbnb?". ARIA indexes the building's actual bylaw document and answers with the exact section citation — no guessing, no fabrication.

What's indexed in the demo

12 representative Canadian condo / strata bylaw sections covering the questions boards actually receive every week:

  • §1.1-1.2 General application, communication
  • §2.1-2.2 Pets — general rules, weight + breed
  • §3.1 Hardwood flooring + acoustic underlay (STC-55 / IIC-50)
  • §4.1 Quiet hours — 11 PM-7 AM weekdays, 12 AM-8 AM weekends
  • §5.1 Smoking — tobacco, cannabis, vape (9 m setback)
  • §6.1 Balcony use — BBQ ban, plants, decorations
  • §7.1 Unit alterations — structural, plumbing, electrical
  • §8.1-8.2 Parking — resident + visitor (24-hour limit)
  • §9.1 Move-in / move-out — CAD $500 deposit, 7-day notice
  • §10.1 Strata fees + late payment
  • §11.1 Common areas — guest limits, supervision
  • §12.1 Short-term rentals — Airbnb / VRBO prohibited

Why this is the wedge for Canadian condos

  • No competitor has it. BuildingLink, Condo Control, BoardSpace are document repositories, not AI lookups with citations.
  • Boards trust it. Citation-grounded answers vs. fabricated rules is the difference between "we should buy this" and "we tried it once."
  • Real-data swap is one call. Replace the demo seed with the building's actual PDF via BylawIndex.ingest_text(org_id, raw_text).
The product moment: A board chair asks ARIA "what's our policy on Airbnb?" — ARIA quotes §12.1 verbatim with the citation badge. Sale closed.

9Multi-turn Conversation

Real assistants need to remember what they just asked. ARIA tracks pending actions per conversation — when ARIA asks for missing info, the next user message is matched against the parked state first, before normal classification.

Three slot-fill flows that work end-to-end

FlowPark triggerResume trigger
Disambiguationbook_amenity returns multiple matchesUser names a tower / block / "first" / "1"
Amount fillpay_dues without an amountUser says "$480" or "480"
Yes/no offerTool-dispatcher offers an alternativeUser says "yes / sure / please"
Decline(any of the above parked)"never mind / cancel / no" → clears state

Pending state expires safely

Every PendingAction carries a created_at timestamp and self-clears after 5 minutes. Abandoned conversations don't leak state into the next chat — and a user returning the next day starts fresh, not mid-flow.

The bug this fixed: In an earlier demo, ARIA offered "I can show notices instead — would you like that?" and the user said "yes I want to see". ARIA had no parked state, the embedding classifier mis-routed "yes" to a payment intent, and the reply hallucinated a payment. With the state machine, "yes" matches the parked yes/no and runs the offered intent.

12Eval Suite & Quality Gates

Every prompt change, intent-classifier tweak, or tool-dispatcher edit auto-runs against a 39-case golden test set. Regressions fail the build before they ship. This is what makes ARIA's quality measurable instead of a hope.

How it works

  • Golden set — 39 cases in tests/evals/cases.py, organised by capability cluster. Each case asserts: expected intent, expected action, structured-prefix emission, language hygiene (no Hindi tokens), currency hygiene (no Rs./₹).
  • FAST mode — LLM stubbed (returns empty), so the deterministic safe_format / _summarize_tool_result path runs. Tests intent routing + tool selection + structured prefixes without burning Gemini quota.
  • Word-boundary token matching — "Rs." won't match inside "loungers."; "hai" won't match inside "Heights".
  • Multi-turn cases — cases prefixed convo:<group>/<step> share a conversation_id so step 2 sees what step 1 parked.
  • Pytest gates — minimum 80% pass rate AND a critical-cases-must-pass list (booking, dues-CAD, currency-leak, admin-block) — both gates green or the build fails.
# Run the eval suite
pytest tests/evals/

# Output: REPORT.md auto-generated in tests/evals/
# - total cases, pass count, pass rate
# - failure breakdown by error type
# - per-case detail for any failures
The discipline this enforces: A prompt edit looks innocent until it breaks 12 cases. The eval suite turns "did this break anything?" from a guess into a 2-minute test run.

cd communityos-aria
alembic upgrade head
python -m aria.society.seed_amenities

# 2. Start T2T (terminal A)
cd t2t_backend
python -m uvicorn app:app --port 8000

# 3. Start ARIA (terminal B)
cd communityos-aria
python chat_api.py     # listens on :8080

# 4. Open the frontend
# file:///.../communityos-aria/frontend/index.html

Container-first

# Both services + Postgres + Redis in one command
docker compose up -d

Production checklist

  • Set APP_ENV=production — triggers fail-fast secret validation
  • Provide real JWT_SECRET (≥32 chars random), GOOGLE_API_KEY, T2T_ADMIN_SECRET
  • Set explicit ALLOWED_ORIGINS for the frontend domain
  • Run alembic upgrade head against the prod DB
  • Replace dummy seed with real amenity import (CSV → DB or admin UI)
  • Point Prometheus at /metrics for both services
  • Configure log shipping to whatever sink you prefer

16Roadmap

Milestone detail

  • Week 1-2 — First real society pilot. Replace dummy seed with the partner society's amenity catalogue (CSV import). Real twin keys for residents. Deploy to staging URL. Onboard 5-10 residents for closed beta.
  • Week 3-4 — Pilot polish. Push notifications on approval prompts. Mobile-responsive frontend audit. Voice pipeline integration (env config already in place). Admin dashboard for ops staff (escalations, ticket trends, content moderation).
  • Month 2-3 — Scale to multi-society. 3-5 societies. Tenant isolation hardening. Per-society customisation (logo, colors, language preference). Reporting dashboards (booking utilisation, ticket SLAs).
  • Month 3+ — Deeper resident lifecycle. Visitor management. Maintenance staff scheduling. Community marketplace (resident-to-resident). Society budget transparency.
What you saw today is what gets shipped. Tested, observable, secure, and built for the way real societies actually work — not the simplified version a demo bot can fake.
